- 面向现场操作员与面试讲解者；演示结构固定为「客服主线、运维补证」。

依据优先级：`prompts/9-doc.md` 的用户裁定与最新隐私修订，其后为仓库契约、流程卡、地图及 #3–#8 决议。扫描报告只提供环境证据，不能代替产品决策。

## 2. 安全与隐私硬门

### 2.1 统一脱敏

所有可见字段统一脱敏，合成数据也不例外。手机号示例只显示 `138****5678`，身份证号示例只显示 `110101********1234`。`trace_id`、`span_id`、规则 ID、工具名等非 PII 标识完整显示，现场实际值填入记录栏。

| 表面 | 必查内容 | 一票否决条件 |
| --- | --- | --- |
| Audit | reason、payload 展开、嵌套对象/数组、截断边界、错误与提示 | 任一完整手机号或身份证号可见 |
| Trace | `status_message`、`skill_observability.block_reason`、全部 attributes、events/异常详情 | 状态、理由或嵌套值泄露原值 |
| 终端与对话 | 客户话术、技术报告、树与审计打印、stdout/stderr、模式提示 | 任一输出通道泄露原值 |
| 全部交互表面 | 复制内容、可访问名称、提示文本、DOM 隐藏文本 | 只遮视觉，仍可复制或被辅助技术读出原值 |

完整原始证据只留在存储层，不得破坏原始审计证据，也不得直接呈现给演示者或面试官。具体实现边界本票不定，见 G7。

契约 `docs/contracts/policy-and-audit.md` §1.3/§3.2 的 reason 示例与最新隐私裁定冲突；当前 Trace/Audit fixture、UI 与终端仍有原 PII 可见路径。这些是目标差异，不是获批例外。本票不复制原示例、不改契约，后续单独裁决与授权，见 G8。

### 2.2 其他硬门

- 只写密钥变量名 `OPENAI_API_KEY`，不读取、打印或粘贴值；replay 应零网络、无需真实密钥。
- cassette 必须过滤 Authorization，不得含 API key、Authorization 内容或其他真实凭据；不公开 cassette 正文。
- R1/R2/R3 均在函数执行前拦截：被拦函数体不进入，不重试、不改道，报告后终止当前 Trace 内子任务。
- 运维只使用合成状态，不执行真实 shell、生产库或破坏性动作。红色节点不能独自证明未执行，必须同时有终端与测试证伪证据。
- 起步、切场景和最终收尾均重建干净演示库，只加载同一组四条种子规则；不清理其他项目数据库或未知 PID。
- 任一隐私、凭据、函数未执行、数据库隔离或模式证据硬门失败，记 BLOCKED 并停止正式彩排，不补 Trace 掩盖。

**运维（未实现门禁后的目标配置，不是第二套运行时）：**

## 9. 录制/回放/自动降级彩排

### 9.1 三模式步骤与提示

**本节均为未实现门禁后的目标动作。**#5 的 `DEMO_LLM_MODE=record`、`DEMO_LLM_MODE=replay`、`DEMO_LLM_MODE=live` 是现有研究结论引用，不代表当前入口已读取选择器。当前只有 replay-only、`record_mode="none"`，不能把设置研究模式名当作当前可运行入口。

| 模式 | 操作员步骤 | 预期提示（目标文案，非当前输出） | 必留证据 |
| --- | --- | --- | --- |
| record | 按固定提示词、用户台词与工具 schema 顺序先录客服完整链路，再录 ops R2/R3 最小集 | 「当前为 record，正在录制对应场景」；无凭据或原 PII | 场景覆盖、终止与未执行事实、三个实际 Trace ID、cassette 安全检查 |
| replay | 对应 cassette 离线重走目标流程，含两个暂停边界与两条运维任务 | 「当前为 replay，使用对应场景录制，零网络」 | 零网络、body 匹配、暂停后回放位置连续、R1/R2/R3 命中与实际 ID |

固定顺序：先 record 客服主线，再 replay 离线冒烟；运维最小集同样有 record/replay 证据；随后安排正式 live 或 APIError 自动降级彩排。各场均按客服后重置、运维两任务后再重置隔离，不累积多场数据再套客服八卡预期。

- 请求匹配必须包含 body；prompt 与工具 schema 数组顺序稳定；录制与回放固定 `max_retries=0`。现有 replay 已有 body 匹配、Authorization 过滤、零重试，不代表三模式已完成。

## 10. README 架构讲解提纲

主图与讲解顺序固定为：

```text
agent 工具调用 -> 埋点 SDK -> 策略引擎 -> SQLite/审计 -> SSE/看板
```

面试讲解可逐字排练：

> 同一套运行时通过配置切换客服与运维。每次工具调用都经过埋点 SDK：先创建调用节点，再由策略引擎同步裁决，无论放行还是拦截都写审计。放行才进入工具函数；拦截就把该调用标为 ERROR，报告并停止子任务。SQLite 保存执行链和审计证据，SSE 把节点开始与结束送到看板。Trace 看过程，审计查裁决，通过关联标识在两边精确定位。

| 真实取舍 | 讲解要点 |
| --- | --- |
| 进程内直连 | 运行时与 FastAPI 同进程，共用存储与引擎，执行前同步裁决；block 函数不执行，MVP 不引入上报 API 或跨进程链路 |
| span 与审计分存 | span 表达执行链和状态，审计保存每次 Skill 调用的裁决及 payload 快照；通过 trace_id+span_id 逻辑关联，不用 payload 填满 span |
| 规则快照按版本热加载 | 写规则与递增版本在同一事务，运行时使用版本化内存快照；保存成功后下一次 evaluate 看到新规则，当前调用不重复求值 |

按 #8 解释时序：span.start 落库/事件 → evaluate → 审计 → allow 执行函数或 block 不执行 → span.end/事件 → block 抛 `PolicyBlocked` → 子任务边界报告并停止。不能讲成先执行再补审计。

统一脱敏不等于引擎支持输出侧检测；引擎仍是调用前、无状态、单次入参声明式匹配。
